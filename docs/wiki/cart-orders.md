# Корзина и заказы

## Клиентский поток

1. `/cart` показывает активную корзину. Для checkout требуется авторизация.
2. Кнопка «Оформить заказ» ведёт на `/checkout`; после успешной авторизации гостя переход выполняется автоматически.
3. `/checkout` отправляет в `POST /orders` только контакты и адрес доставки. Цены, состав заказа, supplier data и суммы определяет API.
4. На одну попытку оформления создаётся `Idempotency-Key`; сетевые повторы используют тот же ключ.
5. После успеха корзина инвалидируется, а пользователь переходит на `/account?order=<id>&created=1`.

Доставка для текущей версии равна нулю. Адрес используется только в immutable snapshot заказа и не сохраняется в профиле или localStorage.

## Личный кабинет

`/account` загружает историю через `GET /orders` порциями по 20. Summary показывает номер, дату, сумму и order/payment/fulfillment статусы. Полный `GET /orders/:id` выполняется только после раскрытия заказа.

Клиент видит snapshots товаров, доставку, свой комментарий и последнюю безопасную payment summary. Supplier SKU/URL и manager comments в клиентский интерфейс не попадают. Отмена требует подтверждения и не восстанавливает корзину.

## Интерфейс менеджера

- `/admin/orders` — список с URL-фильтрами и offset pagination.
- `/admin/orders/[id]` — контакты, доставка, суммы, payment, внутренние snapshots, комментарии и procurement позиции.
- Доступ разрешён только роли `ADMIN`; клиентский guard дополняет, но не заменяет `JwtAuthGuard + AdminGuard` API.
- `SupplierOrder` показывается read-only внутри заказа. Рабочий источник fulfillment — `OrderItem.procurementStatus`.

Frontend предлагает только переходы из серверной state machine. API остаётся окончательным источником истины и может вернуть `409`, после чего query cache обновляется.
